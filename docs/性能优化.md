# 登录页首屏性能

这份记录给面试用。数字都是这次实际测出来的。线上部署之后，还要用同样的方式对 `http://120.27.130.34/` 再跑一遍，下面的「优化后」不是线上分数。

## 问题

登录页是第一个画面，但浏览器要先下载整站脚本和整份 Element Plus 样式，服务端还没有开压缩。

线上 Lighthouse 12.8.2（只看 Performance，报告在任务附件里）打到的就是当前这版构建产物，文件名对得上：`assets/index-NF6z_06S.js`、`assets/index-6Y2rAe4Q.css`。传输体积和文件原始大小几乎一样，说明响应没有 gzip。

| | 移动端 | 桌面 |
| --- | --- | --- |
| 性能分 | 42 | 69 |
| FCP | 10.3 s | 2.4 s |
| LCP | 10.6 s | 2.4 s |
| TBT | 520 ms | 90 ms |
| SI | 11.0 s | 3.9 s |
| CLS | 0 | 0 |

当时 JS 传输 1,179,951 字节（文件 1,179,575 字节），CSS 传输 387,172 字节（文件 386,812 字节）。Lighthouse 估算文本压缩大约能省 1100 KB，未使用的 JavaScript 大约 896 KB。那台机器的 benchmarkIndex 大约是 2870（移动）和 3003（桌面）。

原因有三层：

1. 路由全是静态 `import`，登录页把管理端、顾客端一起打进同一个包。
2. `main.js` 全量 `app.use(ElementPlus)`，并引入 `element-plus/dist/index.css`。
3. Nginx 把静态文件原样发出去，没有 gzip，也没有按文件名哈希做长期缓存。

## 怎么测

对比必须在同一台机器、同一种托管方式下做，否则分数差的是 CPU 和网络，不是这次改动。

- 工具：Lighthouse 12.8.2，只开 performance。
- 移动端用默认预设（模拟慢速 4G、CPU 4 倍降速）。桌面用 `--preset=desktop`。
- 地址是站点根路径 `/`。页面加载后由前端转到登录页，和线上报告一致。
- 优化前、优化后各跑 3 次，表里写中位数。
- 优化前的静态服务不压缩，对齐线上。优化后优先发送构建生成的 `.gz`（对应 Nginx 的 `gzip_static`），`/assets/` 带 `Cache-Control: public, max-age=31536000, immutable`，`index.html` 为 `no-cache`。
- 这次实验机的 benchmarkIndex 大约在 3300 到 3600，比线上那次快，所以本地分数会高于线上同一份未压缩包。本地前后对比才是这次改动的结果。

优化前的本地包和线上文件哈希一致，体积如下（gzip 用 zlib level 6 另算，线上并没有这样发出去）：

| 文件 | 原始 | gzip |
| --- | ---: | ---: |
| `index.html` | 405 B | 301 B |
| `assets/index-NF6z_06S.js` | 1,179,575 B | 387,643 B |
| `assets/index-6Y2rAe4Q.css` | 386,812 B | 52,806 B |
| 合计 | 1,566,792 B | 440,750 B |

Lighthouse 在未压缩服务上记录的传输大约是 1,567,425 B（含少量响应头）。

## 改了什么，为什么

1. **路由懒加载。** 管理端、顾客端、注册页改成动态 `import()`。登录页是首屏，保留静态引入，这样表单组件能和入口一起下载，而不是再多一次往返。Vite 默认会把路由图里所有动态 import 写进 `index.html` 的 modulepreload，登录页仍会预取后台页面，所以在 `vite.config.js` 里把这些路由 chunk 从预加载名单里拿掉。
2. **Element Plus 按需。** `unplugin-vue-components` 和 `unplugin-auto-import` 使用 `ElementPlusResolver`，样式走组件自己的 CSS，不再引入整份 `index.css`。模板里的 `el-*` 会自动带上样式。`ElMessage`、`ElMessageBox` 是脚本里调用的，解析器不会替这种手写 import 补 CSS，所以在用到它们的页面旁边显式引入 `element-plus/es/components/message/style/css` 和 `message-box/style/css`。中文文案不再 `app.use(ElementPlus, { locale })`，改到管理端和顾客端布局上的 `el-config-provider`。登录页用不到日期、分页文案，语言包就不进首屏。
3. **主题还在。** 深青主色 `#1a4d4a` 仍写在 `body` 的 `--el-color-primary` 上，子元素继承，不跟组件 CSS 里的 `:root` 抢同一条规则。主按钮的覆盖选择器加了 `body` 前缀，避免后加载的 `.el-button--primary` 把悬停色改回 Element 默认的浅蓝。
4. **vendor 拆分只拆 Vue。** `vue`、`vue-router`、`@vue/*` 打成 `vue-vendor`，全站共用、体积稳定，适合长期缓存。Element Plus 不收成一个大包：登录页只用表单，表格和日期选择器留在各自路由里。其它第三方库交给 Rollup 按引用关系拆，避免一个 `vendor` 把日期库和 axios 绑进登录页。
5. **登录态和 axios 分开。** 路由守卫只需要 localStorage 的键。这些键原来和 axios 写在同一个模块里，守卫一引用，首屏就要解析整份 axios。键和 `saveSession` 挪到 `src/api/session.js`。登录接口改到点击提交后再 `import()`。
6. **压缩和缓存。** `vite-plugin-compression` 在构建时为超过 1024 字节的 js/css/html 生成同名 `.gz`。`deploy/nginx.conf` 打开 `gzip` 和 `gzip_static`，类型包含 js、css、json、svg、html。带哈希的 `/assets/` 缓存一年并标 `immutable`。`index.html` 不缓存，否则发版后用户还会拿着旧 HTML 去要旧哈希。

## 线上还要再测

上面的 54 → 100、8.7 s → 1.4 s 是本地实验室结果。线上那次移动端 42 分、FCP 10.3 s 是在另一台更慢的机器上、对未压缩的现网测的。配置生效之后，需要对 `http://120.27.130.34/` 再跑 Lighthouse 移动端和桌面端，才能把线上数字写进简历。部署后可以用开发者工具确认：

- JS/CSS 响应有 `Content-Encoding: gzip`
- `/assets/` 响应有 `Cache-Control: public, max-age=31536000, immutable`
- `index.html` 是 `no-cache`
- 登录页网络面板里没有 `EmployeeManage`、`ScheduleBoard`、`ClientBook` 这些 chunk

## 部署

在服务器上，仓库目录里执行：

```bash
git pull
npm install
npm run build
```

然后套用 `deploy/nginx.conf`：

1. 把三个占位符换成这台机器的值：`__FRONTEND_ROOT__`（`dist` 的绝对路径）、`__API_UPSTREAM__`（Express 地址，例如 `127.0.0.1:3000`）、`__SERVER_NAME__`（域名或 IP）。不替换的话 `nginx -t` 会失败，这是故意的。
2. `nginx -V` 里要能看到 `http_gzip_static_module`。没有的话删掉配置里的 `gzip_static`，只保留 `gzip on`，由 Nginx 动态压缩。
3. 如果现在的站点是整站 `proxy_pass` 到 Express、由 Express 托管 `dist`，用这份 `server` 换掉那段反代。静态文件不经过 Node，gzip 和缓存头才会生效。Express 继续只提供 `/api`。
4. `sudo nginx -t && sudo nginx -s reload`
5. 重启现有的 Express 进程（systemd、pm2 或原来的启动方式）。这次没有改接口协议；重启是为了让服务器跑到新代码。不需要执行 `reset:demo`。
